## 9. OTA 回滚测试专项（E07 / E08 细化步骤与预期）

> 本专项为 OTA 双分区升级（阶段 5）验收的收尾项，2026-08-18 起列为后期安排。

### 9.1 背景：回滚路径的验证现状

- **已验证（实跑）**：OTA 排障过程中，每次 `verify fail` 后 Boot 均正确回滚旧分区并正常运行（栈溢出污染数据、firmware_valid 误比较两起 bug 的现场即 E08 回滚行为的实际复现）；
- **未验证**：E07（传输中断）场景未实跑；E08 标准注入流程（改坏一字节重新打包）未完整执行；`fail_code=0x0302` 标记路径未专项验证；
- 两条回滚路径的故障码差异见 9.4。

### 9.2 E07 OTA 传输中断回滚（传输 50% 断电）

| 项 | 内容 |
|---|---|
| 前置 | 系统正常运行；置位 OTA（Modbus 写 40020=0x5A5A 或调试命令 ota）→ 设备进升级模式 `waiting host`；关闭串口助手（占用串口） |
| 步骤 1 | 运行 `%PY% ota_tool.py COMx fw_package.bin` |
| 步骤 2 | [3/6] 数据进度约 40%~60% 时，按板子复位键（等效"传输中断电"；真实断电可拔 USB 重插） |
| 预期 1 | 工具端：连续超时后报错退出（属预期，模拟断电） |
| 预期 2 | 复位后 Boot 读标志区 `upgrade_req=1`（残留）→ 打印 `OTA: upgrade requested, enter upgrade mode` → 进升级模式 |
| 预期 3 | 5s 内无主机握手 → 超时回滚（清升级请求 → 软复位） |
| 预期 4 | 复位后态 0 启动：打印 `OTA: part X valid, fail=00 00`（活动分区不变），App 正常运行，传感器/Modbus 正常 |
| 验证标准 | ① 活动分区与升级前一致；② 旧系统功能完好；③ 可再次正常升级（半截脏数据下次全擦重写，无残留影响） |

### 9.3 E08 OTA 传坏固件（CRC 校验失败回滚）

| 项 | 内容 |
|---|---|
| 前置 | 系统正常运行；用 pack_ota.py 打好正常包，复制一份为坏包 |
| 步骤 1 | 改坏包：脚本把坏包数据区中间一字节 XOR 0xFF（**不改头 crc32 字段**——期望值保持不变，设备侧重算才能对不上） |
| 步骤 2 | 置位 OTA → 关闭串口助手 → 运行 `%PY% ota_tool.py COMx bad_package.bin` |
| 预期 1 | [5/6]：Boot 读 Flash 重算 CRC32 ≠ 头字段期望值 → 打印 `OTA: verify fail local=xxxxxxxx` → 应答失败 → 工具报 `[错误] 设备 CRC32 校验不通过` 并退出 |
| 预期 2 | 0x06 未执行 → 标志区未写（无 upgrade_req=2）→ 设备留在升级模式 → 5s 超时回滚 → 复位 → 旧分区启动 |
| 预期 3 | 串口助手观察：`OTA: part X valid, fail=00 00`（回滚路径故障码为 0，见 9.4）→ App 正常运行 |
| 验证标准 | ① 校验失败被拒绝（不写标志区）；② 旧系统完好；③ 用正常包重新升级成功（坏包无残留影响） |

### 9.4 故障码 0x0302 的触发条件（技术备注）

- `fail_code=0x0302` 只在**态 2 复验失败**时写入（main.c：0x06 已执行、标志区已写 upgrade_req=2、复位后复验不过 → 回滚并置 0x0302）；
- [5/6] 校验失败（E08 场景）**不置 0x0302**——此时 0x06 未执行、标志区未写，走的是升级模式 5s 超时回滚（fail_code=0），启动日志显示 `fail=00 00`；
- 因此 0x0302 的正常触发需要"校验已通过、数据随后损坏"，黑盒难以构造；后期如需专项验证，二选一：
  - a) 升级成功后用串口 ISP 烧录工具破坏新分区数据 → 复位 → 态 2 复验失败 → 观察 `fail=03 02` 与回滚；
  - b) Boot 加临时测试钩子（handle_verify 通过后故意改错写入标志区的 new_crc32），测完还原代码。
